## 오너 결정

- **[확정]** 서버는 오너 집의 리눅스 노트북입니다(전용 서버. 방장 브라우저가 서버가 되는 P2P가 아님).
- **[확정]** 서버 한 대가 **봇 포함 최대 1000명**까지 받습니다. 방 하나의 최대 인원이 아니라 서버 전체 수용량입니다.
- **[확정]** 공개 방: 방을 만들면 목록에 뜨고 누구나 들어올 수 있습니다. 비밀번호를 걸 수도 있습니다.
- **[확정]** 대결 구도는 방장이 정합니다. 기본값은 **유저만**(봇 없음)입니다.
- **[확정]** 이름은 메인 메뉴에 바로 보이고, 처음 접속하면 이름부터 정합니다.
- **[확정]** 서버 노트북: Intel i3-5005U(2코어 4스레드, 2.0 GHz, 터보 없음), DDR3 16 GB, Ubuntu Server LTS. 이미 24시간 돌고 있습니다.
- **[확정]** 모바일도 멀티에 들어올 수 있게 합니다.
- **[확정]** 집 인터넷은 기가 인터넷이고, 100 GB를 쓰면 100 Mbps로 제한(QoS)됩니다. 노트북의 다른 서비스는 가벼운 비동기 작업들입니다.
- **[확정]** strikegy.org는 곧 만료되므로 쓰지 않습니다. 서버 주소(도메인)는 오너가 나중에 알려 줍니다.
- **[확정]** 방 하나는 봇 포함 최대 300명(150 vs 150)입니다.
- **[확정]** 이미 진행 중인 방에 중간 참가할 수 있게 합니다. 사람들이 새 방을 계속 만들기보다 있는 방을 채우게 해서, 방 수가 늘며 계산량이 커지는 것을 막습니다.
- 나머지(아래 [제안])는 오너가 "잘 모르겠다"고 해서 Claude가 기본값을 정합니다. 해 보고 바꿉니다.

## 서버 노트북으로 되는 양 [제안]

i3-5005U는 지금까지 재 온 오너 PC(i5-1135G7)보다 대략 코어 하나가 절반, 전체로는 4분의 1 정도의 힘입니다. 그래서 "봇 1000명을 지금처럼 60 Hz로"는 이 노트북에서 무리일 가능성이 큽니다. 사람 1000명은 CPU보다 업로드 속도가 먼저 문제입니다. 대신 이렇게 맞춥니다.

- **서버 틱 30 Hz**: 봇, 차량, 규칙을 30 Hz로 계산합니다. 사람의 이동 입력은 60 Hz로 받아 그대로 처리합니다(이동 계산은 가볍습니다). 화면은 클라이언트가 보간해서 60 fps 이상으로 그립니다.
- **봇 LOD를 사람 기준으로**: 지금은 "카메라에서 먼 봇은 덜 자주 생각"입니다. 서버에서는 "가장 가까운 사람에게서 먼 봇은 드물게 생각"으로 바꿉니다. 사람 없는 쪽 봇은 아주 가볍게 돕니다.
- **스냅샷은 한 번만 만들기**: 병사마다 상태를 한 틱에 한 번만 인코딩하고, 받는 사람마다 필요한 것만 골라 붙입니다. 사람 수만큼 다시 만들지 않습니다.
- **인원이 아니라 실측 부하로 막기**: 방마다 틱 시간을 잽니다. 노트북 전체가 정한 한도(예: 틱 예산의 75 %)를 넘으면 새 방이나 봇 채우기를 막습니다. 1000명은 서버가 받을 수 있는 최대치이고, 실제 상한은 부하가 정합니다.
- **나중에 서버를 더 붙일 수 있게**: 방 목록이 여러 서버의 방을 함께 보여 주도록 짭니다. 노트북이 모자라면 PC나 두 번째 기계를 붙이면 됩니다.
- **먼저 실측**: 2단계(서버에서 방 하나 돌리기)에 들어가면 이 노트북에서 "봇 n명 방을 m개" 돌려 틱 시간과 메모리를 재고, 그 숫자로 상한을 정합니다. 메모리 16 GB는 방 수십 개에 충분할 것으로 봅니다(맵 하나의 물리 + navmesh).
- **300명 방 하나**(150 vs 150, 대부분 봇): 방 하나는 스레드 하나에서 돌므로 코어 하나를 넘겨 쓸 수 없습니다. 추정으로는 30 Hz 한 틱(33 ms)에 15~20 ms쯤 듭니다. 들어가지만 여유가 크지 않습니다. 이런 방이 동시에 3~4개면 노트북이 찹니다. 사람만 있는 방은 이보다 훨씬 가볍습니다. 사람이 봇 자리를 대신하면 계산이 오히려 줄어듭니다.
- 15 W 노트북이 계속 최대 부하로 돌면 뜨거워집니다. 팬과 먼지를 한 번 봐 주면 좋습니다.

## 인터넷 사용량 [제안]

- 게임 파일(코드, 텍스처, 소리, 맵)은 GitHub Pages에서 받으므로 집 회선을 쓰지 않습니다. 집 회선은 경기 데이터만 씁니다.
- 사람 한 명이 서버 업로드로 초당 약 5~15 KB, 한 시간에 약 18~54 MB를 씁니다. 받는 입력은 초당 2~4 KB 정도입니다.
- 하루 100 GB면 약 1,900~5,500 "사람·시간"입니다. 예를 들어 50명이 하루 3시간씩 하면 약 3~8 GB입니다.
- 제한이 걸린 뒤에도 100 Mbps(초당 12.5 MB)면 동시 접속 사람 약 800~2,500명분입니다. 회선은 CPU보다 먼저 막히지 않을 것으로 봅니다.
- 서버가 하루 사용량을 세어 관리 로그에 남깁니다. 제한에 가까워지면 스냅샷 빈도를 조금 낮추는 장치도 둡니다.

## 서버 주소 [제안]

- 도메인이 정해지기 전에도 개발할 수 있도록, 게임은 서버 주소를 사이트의 설정 파일(예: `public/servers.json`)에서 읽습니다. 주소가 바뀌어도 그 파일만 고치면 됩니다. 나중에 서버를 여러 대 붙일 때도 이 목록을 씁니다.
- 공개 방법은 도메인이 정해지면 고릅니다.
  - 도메인을 Cloudflare에 두면 **Cloudflare Tunnel**: 포트를 열지 않고 집 IP도 숨겨집니다.
  - 아니면 공유기 포트포워딩 + 무료 DDNS 주소 + 자동 인증서(Caddy 같은 리버스 프록시가 Let's Encrypt를 알아서 처리).
  - UDP(모바일용 두 번째 단계)는 어느 쪽이든 UDP 포트 하나를 따로 열어야 합니다.

## 모바일 [제안]

- 연결은 같은 WebSocket이라 모바일 브라우저(안드로이드, iOS)에서 그대로 됩니다. 터치 조작은 이미 있습니다.
- 모바일 회선은 지연이 들쭉날쭉하고 패킷 손실이 있습니다. WebSocket(TCP)은 손실이 나면 잠깐 멈췄다 몰아서 오기 때문에, 모바일 때문에라도 UDP 방식(WebRTC DataChannel. iOS 포함 모든 브라우저 지원)을 두 번째 단계로 넣습니다. 이건 공유기에서 UDP 포트 하나를 열어야 합니다.
- 앱 전환이나 화면 꺼짐으로 연결이 끊기면, 숨은 ID로 60초 안에 다시 들어와 같은 자리·같은 팀으로 이어집니다.
- PC와 모바일이 같은 방에서 싸우면 조준이 불공평할 수 있습니다(터치에는 약한 조준 보정이 있음). 방 설정에 "입력 방식: 모두 / PC만 / 모바일만"을 두고 기본은 "모두"로 합니다. 참가자 목록에 기기 아이콘을 표시합니다.
- 모바일은 지금처럼 낮은 화질 프리셋으로 돌고, 봇 계산과 navmesh를 하지 않으므로 지금 혼자 할 때보다 가볍습니다.

## 봇 계산 분산 [제안]

오너 질문(2026-10-04): "봇만 참가자들이 나눠서 계산하면 안 되나?" → 됩니다. Arma의 "AI 소유권 이전"과 같은 방식입니다.

- **[확정]** 오너가 아래 제안을 받아들였습니다(2026-10-04). 기본으로 켜져 있고, 방장이 방 설정에서 끌 수 있습니다.

- **나누는 것과 남기는 것**
  - 서버는 판정(맞았는지, 피해, 점령, 규칙)과 팀 단위 계획(분대 목표, 콜인)만 합니다. 몇 초에 한 번이라 가볍습니다.
  - 봇의 무거운 부분(시야 확인, 길찾기, 판단, 조준)은 참가자 PC가 맡습니다.
  - 지금 봇은 navmesh를 따라 자기 위치를 직접 정하는 방식(키네마틱)입니다. 맡은 PC가 매 틱 봇의 위치·방향·자세·사격 명령을 보내고, 서버는 사람 입력처럼 검사만 하면 됩니다.
- **누가 맡나**
  - 같은 팀 PC에만, 분대 단위로 맡깁니다. 분대 안의 협동(측면 우회, 부활, 보급)이 한 PC 안에서 돌게 하려는 것입니다.
  - 그 PC의 플레이어 근처 분대를 우선합니다. 그 PC가 이미 그 주변 정보를 받고 있기 때문입니다.
  - 휴대폰은 맡지 않습니다(데스크톱·노트북만). PC마다 프레임 여유를 보고해서 많이 남은 PC에 더 줍니다.
- **치트 방지**
  - 같은 팀 봇만 맡기므로 "적 봇을 바보로 만드는" 조작은 할 수 없습니다.
  - 내 팀 봇을 에임봇으로 만드는 것은 서버가 막습니다. 조준 오차(난이도별 퍼짐)는 서버가 직접 더하고, 회전 속도·이동 속도·연사 속도·탄약은 서버가 검사합니다.
  - 벽 너머 적 정보로 미리 조준하게 하는 정도는 남습니다. 작은 이득이라고 봅니다.
- **맡은 사람이 나가면**: 그 봇들은 바로 다른 PC나 서버로 넘어갑니다. 봇의 기억(본 적, 경로)은 새 주인이 1초 안팎에 다시 파악합니다.
- **아무도 못 맡으면**: 서버가 직접 돌립니다. 사람과 먼 봇은 드물게 생각하는 LOD로 가볍게 돕니다. 예: 협동 vs 봇 모드에서 적 봇, 휴대폰만 있는 방.
- **효과 (추정, 실측 예정)**
  - 봇이 많은 방의 서버 계산이 몇 분의 일로 줄어듭니다. 300명 방도 서버 부담이 사람만 있는 방에 가까워집니다.
  - 맡은 PC의 추가 부담은 300명 봇을 PC 10대가 나누면 대당 30명 정도로, 혼자 150v150을 돌리는 지금보다 훨씬 작습니다.
  - 맡은 PC의 업로드는 봇 하나에 초당 약 0.5~0.7 KB(30명이면 약 20 KB/s)입니다.
- **필요한 것**
  - 봇 코드가 "진짜 상태"가 아니라 "받은 스냅샷"을 보고도 돌게 하는 세계 인터페이스가 필요합니다. 시뮬/화면 분리 단계에서 같이 만듭니다.
  - navmesh는 맵을 만들 때 미리 구워서 GitHub Pages에 파일로 올립니다(`npm run maps`). 서버와 PC 모두 몇 초 걸리던 생성 없이 받아 쓰고, 혼자 하기 로딩도 빨라집니다.
- **지연**: 봇 판단이 서버에 왕복 지연의 절반만큼 늦게 닿습니다(30~100 ms). 봇 반응 시간이 원래 0.38~0.95초라 체감 차이는 작습니다.

## 구조 [제안]

- **서버가 판정합니다.** 서버가 방마다 시뮬(물리, 규칙, 봇, 차량)을 60 Hz로 돌립니다. 클라이언트는 입력만 보내고 상태를 받아 그립니다. 같은 TypeScript 코드가 서버(Node)와 브라우저 양쪽에서 돕니다. Rapier와 recast는 Node에서도 WASM으로 돕니다.
- **프로세스 구성**
  - 관문 프로세스 1개: 접속, 이름, 방 목록, 비밀번호, 수용량 계산을 맡습니다.
  - 방마다 워커 스레드 1개: 그 방의 시뮬을 돌립니다. 노트북 코어를 나눠 씁니다.
- **수용량**: 관문이 서버 전체 인원(사람 + 봇)을 셉니다. 1000을 넘으면 새 방을 만들거나 봇으로 빈자리를 채우는 것을 막습니다. 틱마다 걸린 시간을 재서, 노트북이 버거우면 그 전에 막습니다.
- **연결**
  - 처음에는 WebSocket(wss, 바이너리)으로 합니다.
  - 공개 방법은 둘 중 하나입니다.
    - **Cloudflare Tunnel**: 공유기 포트를 열지 않고 집 IP도 드러나지 않습니다. 인증서도 자동입니다.
    - 공유기 포트포워딩 + DDNS + Let's Encrypt 인증서.
  - 게임 페이지가 https(GitHub Pages)라서 서버도 반드시 wss(인증서)여야 합니다.
  - 나중에 끊김이 문제 되면 UDP 방식(WebRTC DataChannel 또는 WebTransport)을 추가합니다. 연결 코드는 갈아 끼울 수 있게 둡니다.
- **버전**: 접속할 때 프로토콜 버전을 확인합니다. GitHub Pages의 클라이언트와 서버 버전이 다르면 "새로고침" 안내를 띄웁니다.

## 넷코드 [제안]

- **입력**: 매 스텝 `InputState`에 번호를 붙여 보냅니다. 손실에 대비해 최근 2~3개를 같이 보냅니다.
- **내 병사**: 내 화면에서 먼저 움직이고(예측), 서버 결과로 보정합니다. 지형·건물 충돌은 클라이언트에도 있습니다.
- **다른 병사·봇**: 약 100 ms 뒤를 보간해서 그립니다.
- **사격**: 총이 히트스캔이라 서버가 히트박스를 최근 1초 기록해 두고, 쏜 사람이 본 시점으로 되감아 판정합니다(지연 보상).
- **차량·비행기**: 운전자 쪽에서 물리를 계산하고, 서버는 속도와 위치가 말이 되는지만 확인합니다(배틀필드식). 가장 어려운 부분입니다.
- **봇**: 서버에서만 계산합니다. 클라이언트는 navmesh를 만들지 않으므로 로딩이 몇 초 짧아집니다.
- **보내는 것**
  - 반드시 전달되는 이벤트: 처치, 점령, 폭발, 건설, 콜인, 모드 이벤트.
  - 위치·자세 스냅샷: 20~30 Hz. 양자화하고 이전 값과의 차이만 보냅니다. 가깝거나 보이는 것은 자주, 먼 것은 드물게 보냅니다.
- **중간 참가**: 전체 상태(거점, 건설물, 차량, 점수)를 한 번 통째로 보냅니다.
- **대역폭 추정**: 사람 한 명당 서버 업로드 초당 약 5~15 KB. 1000명이 전부 사람이면 약 40~120 Mbps. 봇은 서버 CPU만 쓰고 대역폭은 거의 쓰지 않습니다.
- **CPU 추정**: 150v150 봇전이 i5-1135G7에서 화면 제외 프레임당 약 10 ms였습니다. 서버 노트북(i3-5005U)에서는 위의 "서버 노트북으로 되는 양"을 보세요. 사람은 봇보다 훨씬 가볍습니다(판단·시야 계산 없음).

## 방 [제안]

- **방 목록**: 방 이름, 맵, 모드, 인원/최대, 봇 여부, 🔒(비밀번호), 진행 상태(대기 / 경기 중). 진행 중인 방도 자리가 있으면 바로 들어갈 수 있습니다 [확정].
- **빠른 참가**: 버튼 하나로 자리가 남은 공개 방 중 가장 많이 찬 방에 들어갑니다(사람을 적은 방 수에 모읍니다). 맞는 방이 없을 때만 새 방을 만들자고 권합니다.
- **중간 참가**: 그 경기의 전체 상태를 받은 뒤 배치 화면이 뜹니다. 사람이 적은 팀에 들어가고, 봇이 채우던 방이면 그 팀의 봇 하나와 자리를 바꿉니다.
- **서버가 찼을 때**: 새 방 만들기를 막고 "진행 중인 방에 참가하세요"로 안내합니다.
- **방 만들기**: 이름, 맵, 모드, 팀당 최대 인원(봇 포함 방 전체 최대 300명 [확정]), 대결 구도, 비밀번호(선택), 봇 난이도(봇이 있을 때), 입력 방식(모두 / PC만 / 모바일만, 기본 모두).
- **대결 구도 선택지**
  - 유저만 — 기본값 [확정]
  - 유저 + 빈자리 봇
  - 유저 협동 vs 봇
- **방장**: 방을 만든 사람이 설정을 바꾸고, 경기를 시작하고, 강퇴할 수 있습니다. 방장이 나가면 다음 사람에게 넘어갑니다. 서버가 돌리므로 경기는 끊기지 않습니다.
- **흐름**: 대기 → 경기 → 결과 → 다시 대기. 사람이 다 나간 방은 잠시 뒤 닫힙니다.
- **보안**
  - 비밀번호는 서버에서만 비교하고 저장하지 않습니다.
  - 입력값을 검사합니다: 속도, 연사 속도, 탄약.
  - 접속마다 메시지 수를 제한합니다.
  - 에임핵 같은 클라이언트 치트는 막지 못합니다.

## 이름 [제안]

- 처음 들어오면 메인 메뉴 위에 "이름을 정하세요" 창이 뜹니다. 2~16자, 한글·영문·숫자·`_`·`-`.
- 브라우저에 저장합니다. 메인 메뉴에 늘 보이고, 눌러서 바꿀 수 있습니다.
- 계정이 없으므로 이름을 독점할 수는 없습니다. 같은 방에 같은 이름이 있으면 뒤에 숫자를 붙입니다.
- 브라우저마다 숨은 ID를 하나 저장해서, 끊겼다 다시 들어오면 같은 사람으로 봅니다.
- 혼자 하는 경기에서도 이 이름을 씁니다(지금은 "나").

## 순서 [제안]

0. 이름 정하기 + 메인 메뉴에 이름 표시 (작음)
1. 시뮬과 화면 분리: `Game.ts`(3,400줄), `BotManager`, `buildBlockout`이 메시와 충돌체를 같이 만드는데, 서버는 충돌체만 필요합니다. 가장 큰 작업입니다.
2. Node 서버에서 방 하나, 보병만. 예측·보간·지연 보상. 처음에는 같은 PC(localhost)에서 개발합니다.
3. 방 목록 / 만들기 / 참가 / 비밀번호 / 방장 설정 / 대결 구도
4. 차량, 비행기, 건설, 콜인
5. 방 여러 개 + 워커 + 1000명 상한. 서버 노트북에서 실측합니다.
6. 배포: 도메인이 정해지면 Cloudflare Tunnel 또는 포트포워딩, systemd 자동 재시작, 버전 확인

메뉴: 지금의 "플레이"(혼자, 봇전)는 그대로 두고 메인 메뉴에 "멀티플레이"를 추가합니다.
