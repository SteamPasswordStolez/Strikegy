# 멀티플레이 설계안

상태: **설계 중, 구현 전** (2026-10-04). 오너: "아직 구현하지는 마."

- **[확정]** 오너가 정한 사항입니다.
- **[제안]** Claude의 제안입니다. 오너가 바꿀 수 있습니다.
- **[질문]** 아직 답이 필요한 것입니다.

---

## 오너 결정

- **[확정]** 서버는 오너 집의 리눅스 노트북입니다(전용 서버. 방장 브라우저가 서버가 되는 P2P가 아님).
- **[확정]** 서버 한 대가 **봇 포함 최대 1000명**까지 받습니다. 방 하나의 최대 인원이 아니라 서버 전체 수용량입니다.
- **[확정]** 공개 방: 방을 만들면 목록에 뜨고 누구나 들어올 수 있습니다. 비밀번호를 걸 수도 있습니다.
- **[확정]** 대결 구도는 방장이 정합니다. 기본값은 **유저만**(봇 없음)입니다.
- **[확정]** 이름은 메인 메뉴에 바로 보이고, 처음 접속하면 이름부터 정합니다.

## 구조 [제안]

- **서버가 판정합니다.** 서버가 방마다 시뮬(물리, 규칙, 봇, 차량)을 60 Hz로 돌립니다. 클라이언트는 입력만 보내고 상태를 받아 그립니다. 같은 TypeScript 코드가 서버(Node)와 브라우저 양쪽에서 돕니다. Rapier와 recast는 Node에서도 WASM으로 돕니다.
- **프로세스 구성**
  - 관문 프로세스 1개: 접속, 이름, 방 목록, 비밀번호, 수용량 계산을 맡습니다.
  - 방마다 워커 스레드 1개: 그 방의 시뮬을 돌립니다. 노트북 코어를 나눠 씁니다.
- **수용량**: 관문이 서버 전체 인원(사람 + 봇)을 셉니다. 1000을 넘으면 새 방을 만들거나 봇으로 빈자리를 채우는 것을 막습니다. 틱마다 걸린 시간을 재서, 노트북이 버거우면 그 전에 막습니다.
- **연결**
  - 처음에는 WebSocket(wss, 바이너리)으로 합니다.
  - 공개 방법은 둘 중 하나입니다.
    - **Cloudflare Tunnel**: 공유기 포트를 열지 않고 집 IP도 드러나지 않습니다. 인증서도 자동입니다.
    - 공유기 포트포워딩 + DDNS + Let's Encrypt 인증서.
  - 게임 페이지가 https(GitHub Pages)라서 서버도 반드시 wss(인증서)여야 합니다.
  - 나중에 끊김이 문제 되면 UDP 방식(WebRTC DataChannel 또는 WebTransport)을 추가합니다. 연결 코드는 갈아 끼울 수 있게 둡니다.
- **버전**: 접속할 때 프로토콜 버전을 확인합니다. GitHub Pages의 클라이언트와 서버 버전이 다르면 "새로고침" 안내를 띄웁니다.

## 넷코드 [제안]

- **입력**: 매 스텝 `InputState`에 번호를 붙여 보냅니다. 손실에 대비해 최근 2~3개를 같이 보냅니다.
- **내 병사**: 내 화면에서 먼저 움직이고(예측), 서버 결과로 보정합니다. 지형·건물 충돌은 클라이언트에도 있습니다.
- **다른 병사·봇**: 약 100 ms 뒤를 보간해서 그립니다.
- **사격**: 총이 히트스캔이라 서버가 히트박스를 최근 1초 기록해 두고, 쏜 사람이 본 시점으로 되감아 판정합니다(지연 보상).
- **차량·비행기**: 운전자 쪽에서 물리를 계산하고, 서버는 속도와 위치가 말이 되는지만 확인합니다(배틀필드식). 가장 어려운 부분입니다.
- **봇**: 서버에서만 계산합니다. 클라이언트는 navmesh를 만들지 않으므로 로딩이 몇 초 짧아집니다.
- **보내는 것**
  - 반드시 전달되는 이벤트: 처치, 점령, 폭발, 건설, 콜인, 모드 이벤트.
  - 위치·자세 스냅샷: 20~30 Hz. 양자화하고 이전 값과의 차이만 보냅니다. 가깝거나 보이는 것은 자주, 먼 것은 드물게 보냅니다.
- **중간 참가**: 전체 상태(거점, 건설물, 차량, 점수)를 한 번 통째로 보냅니다.
- **대역폭 추정**: 사람 한 명당 서버 업로드 초당 약 5~15 KB. 1000명이 전부 사람이면 약 40~120 Mbps. 봇은 서버 CPU만 쓰고 대역폭은 거의 쓰지 않습니다.
- **CPU 추정**: 150v150 봇전이 오너 노트북(i5-1135G7)에서 화면 제외 프레임당 약 10 ms였습니다. 봇 1000명이면 코어 2~3개를 계속 쓰는 정도로 봅니다. 사람은 봇보다 훨씬 가볍습니다(판단·시야 계산 없음). 서버 노트북에서 실제로 재 봐야 합니다.

## 방 [제안]

- **방 목록**: 방 이름, 맵, 모드, 인원/최대, 봇 여부, 🔒(비밀번호), 진행 상태(대기 / 경기 중).
- **방 만들기**: 이름, 맵, 모드, 팀당 최대 인원, 대결 구도, 비밀번호(선택), 봇 난이도(봇이 있을 때).
- **대결 구도 선택지**
  - 유저만 — 기본값 [확정]
  - 유저 + 빈자리 봇
  - 유저 협동 vs 봇
- **방장**: 방을 만든 사람이 설정을 바꾸고, 경기를 시작하고, 강퇴할 수 있습니다. 방장이 나가면 다음 사람에게 넘어갑니다. 서버가 돌리므로 경기는 끊기지 않습니다.
- **흐름**: 대기 → 경기 → 결과 → 다시 대기. 사람이 다 나간 방은 잠시 뒤 닫힙니다.
- **보안**
  - 비밀번호는 서버에서만 비교하고 저장하지 않습니다.
  - 입력값을 검사합니다: 속도, 연사 속도, 탄약.
  - 접속마다 메시지 수를 제한합니다.
  - 에임핵 같은 클라이언트 치트는 막지 못합니다.

## 이름 [제안]

- 처음 들어오면 메인 메뉴 위에 "이름을 정하세요" 창이 뜹니다. 2~16자, 한글·영문·숫자·`_`·`-`.
- 브라우저에 저장합니다. 메인 메뉴에 늘 보이고, 눌러서 바꿀 수 있습니다.
- 계정이 없으므로 이름을 독점할 수는 없습니다. 같은 방에 같은 이름이 있으면 뒤에 숫자를 붙입니다.
- 브라우저마다 숨은 ID를 하나 저장해서, 끊겼다 다시 들어오면 같은 사람으로 봅니다.
- 혼자 하는 경기에서도 이 이름을 씁니다(지금은 "나").

## 순서 [제안]

0. 이름 정하기 + 메인 메뉴에 이름 표시 (작음)
1. 시뮬과 화면 분리: `Game.ts`(3,400줄), `BotManager`, `buildBlockout`이 메시와 충돌체를 같이 만드는데, 서버는 충돌체만 필요합니다. 가장 큰 작업입니다.
2. Node 서버에서 방 하나, 보병만. 예측·보간·지연 보상. 처음에는 같은 PC(localhost)에서 개발합니다.
3. 방 목록 / 만들기 / 참가 / 비밀번호 / 방장 설정 / 대결 구도
4. 차량, 비행기, 건설, 콜인
5. 방 여러 개 + 워커 + 1000명 상한. 서버 노트북에서 실측합니다.
6. 배포: Cloudflare Tunnel(또는 포트포워딩), systemd 자동 재시작, 버전 확인

## 질문

- **[질문]** 서버 노트북 사양: CPU(코어 수), 메모리, 리눅스 배포판. 집 인터넷 업로드 속도. 24시간 켜 둘 수 있는지(덮개 닫힘·절전 설정).
- **[질문]** 주소: `play.strikegy.org` 같은 strikegy.org 하위 주소를 써도 되는지, 그 DNS를 어디서 관리하는지. Cloudflare Tunnel은 DNS가 Cloudflare에 있어야 합니다(무료).
- **[질문]** 방 하나의 최대 인원: 사람만으로 몇 명까지인지(예: 32v32), 봇 포함이면 150v150까지 허용하는지.
- **[질문]** 지금의 혼자 하기(플레이 = 봇전, 오프라인)를 그대로 두고 "멀티플레이" 메뉴를 따로 추가하는지.
- **[질문]** 모바일도 멀티에 들어오는지.
