# 멀티플레이 설계안

상태: **설계 중, 구현 전** (2026-10-04). 오너: "아직 구현하지는 마."

- **[확정]** 오너가 정한 사항입니다.
- **[제안]** Claude의 제안입니다. 오너가 바꿀 수 있습니다.
- **[질문]** 아직 답이 필요한 것입니다.

2026-10-04 개정: 오너 노트북 전용 서버 방식에서 **WebRTC P2P(방장 PC가 서버)** 방식으로 바꿨습니다. 같은 날 다시 개정: 목표는 **브라우저만 있으면 되는 것**이라, 방 목록과 연결 설정도 오너 기기가 아니라 **Cloudflare Workers**(무료 플랜)에서 돕니다. 오너 노트북은 쓰지 않습니다.

---

## 오너 결정

- **[확정]** 경기는 **P2P(WebRTC)** 로 합니다. 방에서 인터넷과 기기 성능이 가장 좋은 참가자의 PC가 서버(방장 PC)가 되고, 나머지는 그 PC에 접속합니다. (이전 결정 "오너 노트북 전용 서버, P2P 아님"을 대체합니다.)
- **[확정]** 방 하나는 **봇 포함 최대 300명**(150 vs 150)입니다.
- **[확정]** 직접 연결이 안 되는 사람은 **Cloudflare TURN**(Cloudflare Realtime)으로 중계합니다.
- **[확정]** 치트는 초기에는 막지 않습니다. **안티치트는 나중에 따로** 만듭니다.
- **[확정]** 공개 방: 방을 만들면 목록에 뜨고 누구나 들어올 수 있습니다. 비밀번호를 걸 수도 있습니다.
- **[확정]** 대결 구도는 방을 만든 사람이 정합니다. 기본값은 **유저만**(봇 없음)입니다.
- **[확정]** 이름은 메인 메뉴에 바로 보이고, 처음 접속하면 이름부터 정합니다.
- **[확정]** 모바일도 멀티에 들어올 수 있게 합니다.
- **[확정]** 이미 진행 중인 방에 중간 참가할 수 있게 합니다.
- **[확정]** 봇 계산은 같은 팀 참가자 PC들이 나눠 맡습니다(Arma식). 기본으로 켜져 있고, 방 설정에서 끌 수 있습니다.
- **[확정]** 플레이어도 오너도 **브라우저만 있으면** 됩니다(오너, 2026-10-04). 연결 설정 서버는 Cloudflare Workers + Durable Objects에 둡니다(오너 선택). 지금은 오너의 개인 Cloudflare 계정(`strikegy-signal.ijaeyong46.workers.dev`)에 있고, 오너가 곧 전용 계정을 새로 만들어 옮깁니다.
- **[확정]** strikegy.org는 곧 만료되므로 쓰지 않습니다.
- (참고) 오너 노트북(i3-5005U, Ubuntu Server, 24시간)은 Workers로 옮긴 뒤로 쓰지 않습니다.

## 전체 구조 [제안]

```
          (방 목록, 연결 설정, TURN 인증 발급)
        ┌── 연결 설정 서버: Cloudflare Workers, wss ──┐
        │              │               │           │
     참가자 A ◀══▶ 방장 PC ◀══▶ 참가자 B     참가자 C (휴대폰)
                     ▲                          │
                     ╚═════ Cloudflare TURN ════╝   (직접 연결이 안 될 때만)
   ══ WebRTC 데이터 채널(경기 데이터)    ── WebSocket(연결 설정만)
```

- **방장 중심(스타형)**: 참가자는 방장 PC에만 연결합니다. 모두가 서로 연결하는 메시는 쓰지 않습니다(사람이 n명이면 연결이 n² 개). 예외는 예비 방장으로, 모두가 미리 연결해 둡니다(아래 "방장 이전").
- **방장 PC가 판정합니다.** 물리, 규칙, 피해, 점령은 방장 PC가 계산하고, 참가자는 입력을 보내고 상태를 받아 그립니다. 같은 TypeScript 시뮬 코드를 씁니다.
- **방장의 시뮬은 Web Worker에서 돕니다.** 방장도 게임을 하므로 화면 그리기와 서버 계산이 서로를 막지 않게 합니다. Rapier와 recast는 WASM이라 Worker에서도 돕니다. 탭이 백그라운드로 가면 `requestAnimationFrame`이 멈추므로, 시뮬 틱은 Worker의 타이머로 돌립니다. 열린 데이터 채널이 있는 페이지는 Chrome의 강한 타이머 제한(1분에 한 번)에서 빠지지만, 백그라운드에서 30 Hz가 유지되는지는 실측합니다.
- **연결 설정 서버**(Cloudflare Worker + Durable Object `SignalHub`, `server/worker.ts`): 이름, 방 목록, 비밀번호 확인, WebRTC 연결 정보(SDP/ICE) 전달, 방장 선정, TURN 인증 발급. 경기 데이터는 지나가지 않아서 무료 플랜으로 충분합니다(요청 하루 10만 건, 웹소켓 메시지 20개 = 1건, 잠든 시간은 과금 안 됨). 사람이 없을 때 잠들고, 깨어나면 저장해 둔 방 목록을 복원합니다. 같은 로직(`server/core.ts`)이 Node(`npm run signal`)에서도 돌아 로컬 개발과 테스트에 씁니다.
- **서버 주소는 설정 파일에서 읽습니다** (예: `public/servers.json`). 도메인이 바뀌어도 그 파일만 고치면 됩니다.
- 지금의 "플레이"(혼자, 봇전)는 그대로 두고 메인 메뉴에 "멀티플레이"를 추가합니다.

## 연결: WebRTC와 TURN [제안]

- **데이터 채널 두 개**
  - `state`: `{ ordered: false, maxRetransmits: 0 }`. 위치, 자세, 입력처럼 최신 값만 의미 있는 것. 잃은 패킷은 다시 보내지 않아 TCP처럼 멈췄다 몰아서 오지 않습니다.
  - `events`: 순서와 전달을 보장하는 기본 채널. 처치, 점령, 폭발, 건설, 콜인, 모드 이벤트, 중간 참가 때의 전체 상태.
- **직접 연결이 안 되는 경우**: 일반 인터넷에서 직접 연결은 대략 75~80 %가 성공하고, 나머지는 TURN 중계가 필요합니다. 한국 이동통신망(LTE/5G)은 전부 통신사 NAT(CGNAT) 뒤라서 휴대폰은 거의 항상 TURN을 탑니다. 유선 가정망은 대개 직접 연결됩니다.
- **Cloudflare TURN** [확정]
  - 요금: SFU와 합쳐 월 1,000 GB 무료, 그 뒤 GB당 $0.05.
  - 인증: 연결 설정 서버(Worker)가 Cloudflare API(`POST https://rtc.live.cloudflare.com/v1/turn/keys/<키 ID>/credentials/generate-ice-servers`, `ttl` 초)로 짧게 쓰는 인증을 받아 참가자에게 줍니다. API 토큰은 Worker 비밀값(`wrangler secret put CF_TURN_KEY_ID` / `CF_TURN_API_TOKEN`)에만 두고 브라우저에는 절대 넣지 않습니다. 인증 유효 시간은 경기 길이를 넘게(예: 3시간) 잡습니다.
  - STUN도 Cloudflare 것(`stun.cloudflare.com`)을 씁니다.
  - 사용량 추정: 중계되는 사람 한 명이 시간당 약 50~70 MB(받고 보내기 합). 월 1,000 GB면 약 15,000 "중계된 사람·시간"입니다. 연결 설정 서버가 TURN을 쓴 연결 수를 세어 로그에 남깁니다.
  - 방장 자신이 TURN으로만 연결되면 모든 데이터가 중계를 거칩니다. 그래서 그런 PC는 방장으로 뽑지 않습니다.
- **버전**: 연결 설정 서버와 방장 PC 모두 접속할 때 프로토콜 버전을 확인합니다. 다르면 "새로고침" 안내를 띄웁니다.

## 방장 고르기 [제안]

방이 만들어지거나 경기가 시작될 때, 그리고 사람이 들어오고 나갈 때 점수를 다시 매깁니다. 경기 중에는 방장이 나갈 때만 바꿉니다.

- **후보에서 빼는 것**: 휴대폰과 태블릿, 다른 사람과 TURN으로만 연결되는 PC, 프레임이 이미 모자란 PC.
- **재는 것**
  | 항목 | 방법 | 비중 |
  |---|---|---|
  | 다른 사람들과의 지연 | `getStats()`의 `currentRoundTripTime`. 평균과 **가장 느린 사람과의 지연** | 큼 |
  | 업로드 여유 | 데이터 채널로 2~3초 시험 전송(대기실에서) | 큼 |
  | CPU 여유 | 실제 시뮬 스텝 수백 번을 Worker에서 돌려 시간 측정, 지금 프레임 시간 | 중간 |
  | 전원 | 배터리로 돌고 있으면 감점(`navigator.getBattery`가 있는 브라우저만) | 작음 |
- **순서**: 대기실에서 누구나 연결 설정 서버를 거쳐 상위 후보 3~4명과 시험 연결을 합니다(전원과 다 연결하지 않음). 점수 1위가 방장, 2위가 예비 방장입니다. 결과는 연결 설정 서버가 기록하고 모두에게 알립니다.
- **필요한 업로드**: 사람 한 명당 방장 업로드 초당 약 5~15 KB. 사람 64명이면 약 3~8 Mbps, 150명이면 약 6~18 Mbps입니다. 한국 유선 인터넷이면 대부분 됩니다.
- **필요한 CPU**: 봇 300명을 방장 혼자 돌리면 150v150 기준 i5-1135G7에서 프레임당 약 10 ms(화면 제외)였습니다. 봇 계산 분산이 켜져 있으면 방장은 판정만 하므로 훨씬 가볍습니다.

## 방 인원과 방장 PC의 한계 [제안]

- 방은 봇 포함 300명 [확정]. 봇이 많은 방은 문제없습니다(봇은 연결을 쓰지 않음).
- **사람 수에는 별도 상한을 둡니다.** Chrome은 한 페이지에 WebRTC 연결을 500개까지만 열 수 있고, 실제로는 연결이 수십 개를 넘으면 암호화(DTLS)와 SCTP 처리로 CPU가 꽤 듭니다. 기본 사람 상한은 64명으로 시작하고, 2단계에서 방장 PC로 연결 수를 늘려 가며 실측한 뒤 올립니다. 방장 PC 점수가 높으면 더 받습니다.
- 사람이 자리를 채우면 그만큼 봇이 빠지고 300명은 그대로입니다.

## 방장 이전 [제안]

- **예비 방장**: 점수 2위. 모든 참가자가 예비 방장과도 연결을 미리 열어 둡니다(데이터는 거의 안 보냄).
- **상태 복제**: 방장이 1~2초마다 전체 상태(병사, 거점, 건설물, 차량, 점수, 모드 타이머)를 예비 방장에게 보냅니다. 중간 참가 때 보내는 것과 같은 직렬화입니다.
- **방장이 정상적으로 나갈 때**: 최신 상태를 넘기고 "방장 교대"를 알린 뒤 나갑니다. 멈춤은 1초 안팎입니다.
- **방장이 갑자기 끊길 때**: 참가자들이 1.5초 동안 아무것도 못 받으면 예비 방장에게 붙습니다. 예비 방장은 마지막 복제 상태에서 이어 갑니다. 최대 2초가량 되돌아갈 수 있고, 멈춤은 2~3초입니다. 그 사이의 처치나 점령은 사라질 수 있습니다.
- 새 방장이 다음 예비 방장을 뽑고, 연결 설정 서버에 알립니다.
- 예비 방장도 없으면 남은 사람끼리 다시 뽑고, 연결 설정 서버를 거쳐 다시 연결합니다(5~10초).

## 넷코드 [제안]

- **입력**: 매 스텝 `InputState`에 번호를 붙여 보냅니다. 손실에 대비해 최근 2~3개를 같이 보냅니다.
- **내 병사**: 내 화면에서 먼저 움직이고(예측), 방장 결과로 보정합니다.
- **다른 병사·봇**: 약 100 ms 뒤를 보간해서 그립니다.
- **사격**: 방장이 히트박스를 최근 1초 기록해 두고, 쏜 사람이 본 시점으로 되감아 판정합니다(지연 보상). 방장 본인은 지연이 0이라 유리한데, 지연 보상이 이 차이를 일부 줄여 줍니다.
- **차량·비행기**: 운전자 쪽에서 물리를 계산하고, 방장은 속도와 위치가 말이 되는지만 확인합니다(배틀필드식).
- **보내는 것**: 위치·자세 스냅샷은 20~30 Hz. 양자화하고 이전 값과의 차이만 보냅니다. 가깝거나 보이는 것은 자주, 먼 것은 드물게 보냅니다. 스냅샷은 병사마다 한 틱에 한 번만 인코딩하고 받는 사람별로 골라 붙입니다.
- **틱**: 방장 시뮬 30 Hz, 사람 이동 입력은 60 Hz로 받습니다.
- **중간 참가**: 전체 상태를 `events` 채널로 한 번 보낸 뒤 배치 화면을 띄웁니다.

## 봇 계산 분산 [확정, 세부는 제안]

- 방장 PC는 판정과 팀 단위 계획(분대 목표, 콜인)만 합니다.
- 봇의 무거운 부분(시야, 길찾기, 판단, 조준)은 같은 팀 데스크톱·노트북들이 분대 단위로 맡습니다. 그 PC의 플레이어 근처 분대를 우선합니다. 휴대폰은 맡지 않습니다.
- 맡은 PC는 봇의 위치, 방향, 자세, 사격 명령을 방장에게 보냅니다. 이 데이터도 방장을 거치므로 연결이 늘지 않습니다.
- 맡은 사람이 나가면 그 봇들은 다른 PC나 방장 PC로 넘어갑니다. 아무도 못 맡으면 방장이 직접 돌리고, 사람과 먼 봇은 드물게 생각하게 합니다.
- 맡은 PC의 추가 업로드는 봇 하나에 초당 약 0.5~0.7 KB입니다.
- navmesh는 맵을 만들 때 미리 구워 GitHub Pages에 올립니다(`npm run maps`). 로딩도 빨라집니다.

## 모바일 [제안]

- WebRTC 데이터 채널은 iOS를 포함한 모바일 브라우저 모두에서 됩니다. 휴대폰은 대부분 TURN을 탑니다.
- 휴대폰은 방장도, 봇 계산도 맡지 않습니다.
- 앱 전환이나 화면 꺼짐으로 끊기면, 숨은 ID로 60초 안에 다시 들어와 같은 자리, 같은 팀으로 이어집니다.
- 방 설정의 "입력 방식: 모두 / PC만 / 모바일만"은 기본 "모두"로 하고, 참가자 목록에 기기 아이콘을 표시합니다.

## 방 [제안]

- **방 목록**(연결 설정 서버): 방 이름, 맵, 모드, 인원/최대, 봇 여부, 🔒, 진행 상태. 진행 중인 방도 자리가 있으면 바로 들어갈 수 있습니다 [확정].
- **빠른 참가**: 자리가 남은 공개 방 중 가장 많이 찬 방으로 보냅니다.
- **방 만들기**: 이름, 맵, 모드, 최대 인원(봇 포함 300 [확정]), 대결 구도(유저만 [기본, 확정] / 유저 + 빈자리 봇 / 유저 협동 vs 봇), 비밀번호, 봇 난이도, 입력 방식, 봇 계산 분산 켜기/끄기.
- **방을 만든 사람과 방장 PC는 다릅니다.** 방을 만든 사람(방 주인)이 설정, 시작, 강퇴를 맡고, 서버 역할은 점수 1위 PC가 맡습니다. 방 주인이 나가면 주인 권한은 다음 사람에게 넘어갑니다.
- **흐름**: 대기(이때 방장 고르기 측정) → 경기 → 결과 → 다시 대기. 사람이 다 나간 방은 목록에서 사라집니다.
- **비밀번호**: 연결 설정 서버에서만 비교하고 저장하지 않습니다. 방장 PC에는 보내지 않습니다.

## 치트 [확정: 초기에는 받아들임, 나중에 안티치트]

P2P에서는 방장 PC가 판정을 하므로, 방장은 개발자 도구로 판정을 바꿀 수 있습니다. 초기에는 받아들이고, 나중에 안티치트를 만들 때 쓸 수 있도록 지금부터 이렇게만 해 둡니다.

- 방장이 처치, 점령, 경기 결과 같은 주요 이벤트를 연결 설정 서버에 짧게 기록합니다. 나중에 참가자들의 기록과 비교하는 데 씁니다.
- 방장 PC도 참가자의 입력을 검사합니다: 속도, 연사 속도, 탄약, 회전 속도.
- 강퇴 투표와 신고 버튼은 방 기능에 넣습니다.
- 나중에 안티치트를 만들 때 생각할 수 있는 방법(아직 정하지 않음): 참가자들이 방장 결과를 표본으로 다시 계산해 보는 교차 검증, 문제 있는 방장 PC를 후보에서 빼는 평판 기록, 공개 방만 전용 서버로 돌리기.

## 이름 [제안]

- 처음 들어오면 메인 메뉴 위에 "이름을 정하세요" 창이 뜹니다. 2~16자, 한글·영문·숫자·`_`·`-`.
- 브라우저에 저장하고, 메인 메뉴에 늘 보이며, 눌러서 바꿀 수 있습니다.
- 같은 방에 같은 이름이 있으면 뒤에 숫자를 붙입니다.
- 브라우저마다 숨은 ID를 하나 저장해서, 끊겼다 다시 들어오면 같은 사람으로 봅니다.
- 혼자 하는 경기에서도 이 이름을 씁니다(지금은 "나").

## 라이브러리 [제안]

- WebRTC API(`RTCPeerConnection`)를 직접 쓰고, 연결 설정은 우리 연결 설정 서버로 합니다. 방 목록이 어차피 그 서버에 있기 때문입니다.
- 참고만 한 것: PeerJS(연결 설정을 감싸 줌, 채널 세부 설정에는 불편), Trystero(공개 중계로 서버 없이 연결, 안정성과 방 목록이 약함), geckos.io(브라우저↔Node 서버용이라 P2P가 아님).

## 순서 [제안]

0. 이름 정하기 + 메인 메뉴에 이름 표시 (작음)
1. 시뮬과 화면 분리: `Game.ts`(3,400줄), `BotManager`, `buildBlockout`이 메시와 충돌체를 같이 만드는데, 방장 Worker는 충돌체만 필요합니다. 가장 큰 작업입니다. 시뮬이 Worker에서 돌게 하는 것까지 포함합니다.
2. 같은 PC의 두 탭으로 방장 1 + 참가자 1, 보병만. 예측, 보간, 지연 보상. 연결 설정 서버는 localhost(`npm run signal`) 또는 Workers.
3. 방 목록, 만들기, 참가, 비밀번호, 방 설정, 대결 구도. 방장 고르기와 TURN(Cloudflare) 연결.
4. 방장 이전, 중간 참가, 재접속.
5. 차량, 비행기, 건설, 콜인, 봇 계산 분산.
6. 실측: 방장 PC의 사람 상한(연결 수), 300명 방, 백그라운드 탭에서의 틱 유지, TURN 사용량.
7. 배포: 연결 설정 서버는 `npm run signal:deploy`(Workers). 전용 Cloudflare 계정으로 옮기기.

## 질문

- **[질문]** 전용 Cloudflare 계정: 오너가 새로 만들면 옮깁니다(아래 "계정 옮기기").
- **[질문]** Cloudflare 계정에서 TURN 키를 만들어야 합니다(대시보드 → Realtime → TURN). 키 ID와 API 토큰은 Worker 비밀값으로만 넣습니다(저장소에는 넣지 않음).

## 계정 옮기기

1. `npx wrangler logout`, 새 계정으로 `npx wrangler login --device`.
2. `npm run signal:deploy` → 새 주소 `https://strikegy-signal.<새 계정>.workers.dev`.
3. (TURN을 쓰면) 새 계정에서 TURN 키를 만들고 `npx wrangler secret put CF_TURN_KEY_ID`, `CF_TURN_API_TOKEN`.
4. `public/servers.json`의 주소를 `wss://strikegy-signal.<새 계정>.workers.dev/signal`로 바꿔 푸시.
5. 옛 계정의 Worker 삭제(`npx wrangler delete`를 옛 계정 로그인 상태에서).
